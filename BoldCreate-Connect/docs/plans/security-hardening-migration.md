## 1. The question: should every gateway request be handled by `api`, with no database access in the gateway?

**Yes, as the target.** The gateway is the only public entry for SDK and MCP traffic, so it is the most exposed process, and it holds a database role with `BYPASSRLS`. A compromised gateway pod with database access reads every tenant. With no database access it can only ask `api`, which checks the key again, applies row-level security and returns one tenant's data.

**Today it is only partly true.** Staging and production set `DATA_SOURCE: api`, so key authentication, the server list, upstream credentials and the usage record go through `api`. But the gateway process still starts a database pool and still reads and writes the database for other things (section 3), the default in code is still `database`, preproduction does not set `DATA_SOURCE`, and the gateway readiness check depends on the database. So the gateway still needs the `app_gateway` role (with `BYPASSRLS`) to start and to stay ready.

**Cost to know about.** Routing everything through `api` adds a hop and database work. One MCP `tools/call` makes up to four internal calls (authenticate, servers, access, usage), and each re-checks the key and opens a database transaction. This multiplies load on a 1 vCPU database, so the security target and the capacity plan must be done together (items S2.3, S2.11 and CAP-12).

## 2. Target architecture

- **`gateway` has no database access.** No `DATABASE_URL`, no role, no `@boldcreate-integrations/db` import. It authenticates keys and resolves installs through `api` (internal, workload identity), behind a short cache. It never holds sealed data and organization keys together.
- **No role has `BYPASSRLS`** except the migrator (today `gateway` and the migrator do).
- **Tenant isolation does not rest on a `WHERE` clause alone.** Tables that carry tenant data have row-level security, and each table without it has a written reason.
- **`admin` has least privilege.** It reaches tenant data through `api`, or its role is read-only on tenant data.
- **KMS permissions are split** by service (encrypt, decrypt), and the gateway needs none if it never unseals.
- **Internal calls cannot be replayed.** Workload tokens on credential-resolving routes are single use.
- **Every deployed pod proves its environment** with `DEPLOY_ENV`.
- **No credential in git**, and CI blocks a commit that adds one.
- **Default-deny network**, per service, including the gateway and admin.
- **A changed or new MCP tool does not reach an agent unreviewed**, and sign-up is throttled.
- **A failure of `api` or the database never admits a key.** The gateway fails closed with `503`.

## 5. Scope

This plan holds the **core architecture** items (the gateway and database access, row-level security, `admin` privilege, KMS and internal-call hardening), what is **critical now**, and what is **recommended before the first real customers**. The rest of the review was dropped on 2026-10-22 as not needed yet: the monthly purge job (S7), admin OIDC or MFA, audit retention, organization soft-delete, org key rotation, and the later items of S5, S6, S8, S9 and S10. They stay in git history and can come back when customers, third-party plugins or public sign-up come closer.

### Tiers

**Critical now:** S0.1, S0.3, S0.5, S2.8, S2.9, S6.1, S6.2, S9.6, S11.1.

**Core architecture** (the main work; S2 is the largest change): S2.1 to S2.14, S3.1 to S3.5, S4.1, S6.7, S9.4, S9.8, S9.10, S6.5, S1.5.

**Gates** (required only when the event happens): S10.1 and S10.2 before any third-party plugin is published; S10.3 before public sign-up opens.

**Recommended before the first real customers:** S5.1, S5.2, S8.2, S8.3, S9.1, S9.2, S4.1 to S4.5, and the base-image pin in S1.4.

Done already: S0.2 (migration job only), S0.4, S0.6, S1.1 to S1.3, S2.0, S8.1.

Until S2 lands, `gateway` keeps its database role; that exception is recorded in [decisions.md](../architecture/decisions.md) ("The gateway reads the database for now"), and S4.1 limits what a compromised gateway can reach.

## Order

1. **S0 first**, in any order. Then the critical code items S6.1, S6.2, S9.6.
2. **Quick wins for the gateway (small, no new service):** S2.8 (api mode only), S2.9 (readiness off Postgres), S4.1 for the gateway (network policy). These close issues 2, 3 and 4 and should land before any scale-out work.
3. **Remove the database from the gateway:** S2.10, then S2.5 and S3.1, with S2.6 and S2.7. S2.3 and S2.11 reduce the added hop cost and should land with or just before S2.5.
4. **Credentials and replay:** S6.7 before the gateway resolves credentials through `api` at scale; S2.4 and S9.4 follow; S2.12, S2.13 and S2.14 alongside S2.11.
5. S4.1 can start after S0 and must land before S2.5 so the internal path is the only route; it needs the Postgres and Redis addresses and the ingress path first. S4.5 with the first mesh or TLS decision.
6. S9.8 merges into S2.3. S3.2 to S3.5 are independent of S2. S5.1 comes before S5.2.
7. S10.1 and S10.2 before any third-party plugin; S10.3 before public sign-up.
8. **Capacity link:** the pooler (CAP-07), load shedding (CAP-08) and the gateway key cache (CAP-12) in `connection-pooling.md` and S2.3, S2.9 and S2.11 here are the same work seen from two sides; do them together.

## Exit criteria

- No credential in git or its history; CI blocks a new one.
- `apps/gateway` imports nothing from `packages/db`, starts with no `DATABASE_URL`, and no role except the migrator has `BYPASSRLS`.
- A deployed gateway refuses to start unless it uses `api`, and its readiness does not depend on Postgres.
- Every manifest sets `DEPLOY_ENV`; the apps refuse to start without it in a container.
- Each namespace limits traffic per service, including `gateway` and `admin`; every multi-replica service has a PodDisruptionBudget.
- A revoked key stops working within the cache TTL, and every tool call leaves an audit record or a visible failure metric.
- Gateway overhead p95 under 50 ms (S2.7) with the extra hop, at the stable rate in `connection-pooling.md`.
